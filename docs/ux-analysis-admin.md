# 관리자 UX 분석

> 2026-04-11 코드베이스 기준

<br>

## 현재 구조

관리자는 별도 바이너리(`main_admin.dart`)로 접근하는 `AdminDashboard`를 사용한다.
8개 탭이 있다.

```
탭 0: 홈           환영 메시지 + 기능 카드 (운영 지표 없음)
탭 1: 견적문의      견적문의 관리
탭 2: 중개사 관리    인증 처리 + FCM 발송
탭 3: 중개사 성과    통계
탭 4: 매물 관리
탭 5: 매물 검증     등기 확인 후 활성화
탭 6: 활동 로그
탭 7: 매칭 관리
```

<br>

---

## 운영 현황을 한눈에 파악할 수 없다

### 1. 홈 탭에 핵심 지표(KPI)가 없다 `A-001`

탭 0(홈, `admin_dashboard.dart:302-369`)이 환영 메시지와 기능 카드 목록만 보여준다.
관리자가 앱을 열었을 때 즉시 알아야 하는 정보:

- 인증 대기 중개사 **N명** → 탭 2에 가야 알 수 있음
- 미검증 매물 **N건** → 탭 5에 가야 알 수 있음
- 미처리 견적 **N건** → 탭 1에 가야 알 수 있음
- 오늘 신규 매물/사용자 수 → 확인 방법 없음

8개 탭을 직접 돌아다녀야 무엇이 쌓여있는지 알 수 있다.

SaaS 관리자 대시보드 설계의 업계 표준(Mixpanel, Amplitude, Stripe Dashboard)은
로그인 후 첫 화면에서 "즉시 행동이 필요한 항목 수"를 보여준다.

→ 홈 탭에 Firestore 카운트 쿼리 기반 실시간 KPI 위젯.
  `where('status', isEqualTo: 'pending').count()` 수준의 단순 쿼리.

<br>

### 2. 탭에 미처리 건수 배지가 없다 `A-002`

모바일 헤더(`admin_dashboard.dart:89-109`)와 데스크톱 헤더
(`admin_dashboard.dart:162-189`) 모두 탭 라벨만 표시한다.

"중개사 관리" 옆에 "③"이 붙어 있으면 바로 알 수 있지만,
현재는 탭을 열어봐야 대기 건이 있는지 없는지 알 수 있다.

→ 각 탭에 미처리 건수 배지 (`Badge` 위젯).

<br>

## 수동 병목 — 스케일을 막는 구조

### 3. 중개사 인증이 완전 수동이다 `A-003`

**현재 흐름:**
중개사 가입 → 관리자가 `admin_broker_management.dart:495-510`에서 수동 확인
→ `verified: true` 설정 → `broker_verified` FCM 발송.

인증 완료 알림은 구현되어 있다. 그러나 **인증 신청이 들어왔을 때
관리자에게 알림이 가는지 확인할 수 없다.**
관리자가 대시보드를 직접 열어보기 전까지는 신청이 쌓여있는지 모른다.

스케일 문제: 중개사 1명당 인증에 평균 5분이 걸린다고 가정하면,
일 10건이면 50분, 일 50건이면 4시간 이상이 필요하다.
2025년 기준 전국 공인중개사 약 11만 명 (한국공인중개사협회)이고,
플랫폼 성장에 따라 일 인증 요청이 급증할 수 있다.

→ **단기**: 인증 신청 시 관리자에게 FCM 알림 + 홈 KPI에 대기 건수 표시.
→ **중기**: 공공데이터포털의 사업자등록정보 진위확인 API(국세청) +
  중개업등록 조회 API(국토교통부)로 자동 검증.

<br>

### 4. 매물 검증이 완전 수동이다 `A-004`

**현재 흐름:**
매도자 등록(pending) → 관리자가 `admin_property_verification_page.dart`에서
등기 정보를 수동 확인 → 승인(active) → 지역 중개사에게 배포.

매물당 등기 확인에 5~10분이 소요된다. 일 10건이면 관리 가능하지만,
매물 시딩(대리 등록 + 외부 임포트)이 본격화되면 일 50건 이상이 될 수 있고,
이 경우 관리자 1명의 하루 업무 대부분이 검증에 소비된다.

→ **단기**: 등기부등본 PDF 첨부 필수화로 검토 시간 단축.
→ **중기**: 등기 자동 조회 API 연동.

<br>

### 5. 대리 등록이 관리자만 할 수 있다 `A-005`

전화로 매도자 정보를 받아 관리자가 대신 등록하는 구조다.
초기 매물 시딩에 유용하지만, 관리자 한 명에게 의존한다.
영업팀이 생기면 그들도 대리 등록을 할 수 있어야 한다.

→ 내부 영업팀용 간소화된 대리 등록 도구 (관리자 권한 하위 레벨).

## UI/에러 처리 문제

### 6. 매물 검증 다이얼로그에서 주소가 빈 줄로 나올 수 있다 `A-006`

`admin_property_verification_page.dart`의 여러 지점(line 260, 508, 579, 691)에서
`property.roadAddress`를 다이얼로그 메시지에 직접 삽입한다.
`roadAddress`가 빈 문자열(`""`)이면 다이얼로그 메시지가 이렇게 보인다:

```
[빈 줄]

이 매물을 검증하시겠습니까?
```

빈 문자열은 null이 아니므로 null-coalescing(`??`)으로 잡히지 않는다.

→ `property.roadAddress.isEmpty ? '주소 미입력 매물' : property.roadAddress`.

<br>

### 7. 중개사 관리에서 재시도 시 로딩 표시가 없다 `A-007`

`admin_broker_management.dart:224-253`에서 에러 상태에서 "다시 시도" 버튼이 있지만,
재시도 중 로딩 인디케이터가 표시되지 않는다. 재시도도 실패하면
이전 에러 메시지가 그대로 남아서 "눌렀는데 아무 일도 안 일어남"으로 보인다.

→ 재시도 시 로딩 스피너 표시 + 에러 메시지 갱신.

<br>

### 8. 좁은 데스크톱 화면에서 레이아웃이 깨진다 `A-008`

`admin_dashboard.dart:165-187`에서 500~900px 너비 구간에
`isNarrow`, `isNarrowDesktop` 등 다중 조건 분기가 있다.
이 구간에서 탭 네비게이션 간격이 불일치하고, `LayoutBuilder` 중첩으로
불필요한 리빌드가 발생한다.

반응형 설계의 원칙(Material Design Adaptive Layouts)은 브레이크포인트를
3개 이하(compact/medium/expanded)로 제한할 것을 권장한다.

→ 브레이크포인트 정리 + 중첩 `LayoutBuilder` 제거.

<br>

## 운영 시나리오별 끊기는 지점

**시나리오 1: 중개사 가입 처리**
```
신청 → 관리자에게 알림 [불명확] → 인증 처리 → 중개사에게 FCM [구현됨]
```
관리자가 신청 사실을 인지하는 수단이 빠져 있다.

**시나리오 2: 매물 검증 처리**
```
등록(pending) → 관리자 알림 [불명확] → 등기 확인 → 승인 → 중개사 알림
```
양 증가 시 관리자 1인 병목.

**시나리오 3: 구매자-중개사 매칭 실패**
```
구매자 문의 → 자동 배정 → 해당 지역 중개사 없음 → ???
```
`mls_property_service.dart:2334-2354`에서 승인된 중개사가 1명일 때만 자동 배정.
0명이면 문의가 `pending` 상태로 방치되고, 관리자에게 알림도 가지 않는다.
이 케이스에 대한 처리 플로우가 정의되어 있지 않다.
