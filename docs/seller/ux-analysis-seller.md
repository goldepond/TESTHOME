# 매도자 UX 분석

> 2026-04-11 코드베이스 기준

<br>

## 현재 구조

매도자는 `MainPage`의 4개 탭을 사용한다.
등록 매물이 있으면 탭 1(내 매물)이 기본이고, 없으면 탭 3(탐색)이 기본이다.
이 분기는 `main_page.dart:249-270`의 `_updateInitialTabByPropertyExistence()`에서 처리된다.

```
탭 0: 매물 등록 (3단계 간소화)
탭 1: 내 매물 대시보드 — 상태별 필터 + 매물 카드 + 빠른 방문승인
탭 2: 시세 조회 — 실거래가 + 내 매물 비교
탭 3: 탐색 — 공개 매물 목록
```

<br>

## 등록 흐름 문제

### 1. 가격을 입력할 때 즉시 피드백이 없다 `S-001`

`mls_quick_registration_page.dart:311-322`의 `_onPriceChanged()`는 가격이 바뀔 때
검증 없이 auto-save만 스케줄링한다. 0원을 입력해도, 100억을 입력해도
제출 버튼을 누를 때까지 아무 경고가 뜨지 않는다.

UX 리서치에 따르면 폼 입력 시 실시간 인라인 검증은 제출 시점 검증 대비
오류 수정 시간을 22% 단축한다 (Luke Wroblewski, *Web Form Design*, A Book Apart).

→ 가격 범위 실시간 검증. 지역 시세 대비 ±50% 이상이면 경고 표시.

<br>

### 2. 전화번호를 아무 형식으로나 저장할 수 있다 `S-002`

매도자 전화번호는 세 곳에서 검증 없이 저장된다:

| 위치 | 코드 | 문제 |
|------|------|------|
| 등록 시 | `mls_quick_registration_page.dart:277` | `.text.trim()`만 확인 |
| 제출 시 | `mls_quick_registration_page.dart:2754` | 동일 |
| 승인 다이얼로그 | `visit_request_quick_sheet.dart:420` | 빈 값 여부만 확인 |

입력 필터(`FilteringTextInputFormatter.allow(RegExp(r'[0-9\-]'))`)가 있어서
숫자와 하이픈만 허용되지만, `123-4567` 같은 비정상 포맷도 통과한다.
한국 휴대전화 번호(`010-XXXX-XXXX`, 11자리)를 검증하는 정규식이 없다.

이 번호는 방문 요청 승인 시 중개사에게 전달되므로, 잘못된 번호가 저장되면
중개사가 매도자에게 연락할 수 없다.

→ `RegExp(r'^01[016789]-?\d{3,4}-?\d{4}$')` 검증 추가.

<br>

### 3. 여러 장의 사진을 올릴 때 진행률이 보이지 않는다 `S-003`

`mls_quick_registration_page.dart:73-74`에 `_uploadProgress`와 `_totalImages` 변수가
선언되어 있지만, UI 어디에서도 사용되지 않는다. 10장의 사진을 올리면
업로드가 끝날 때까지 화면이 멈춘 것처럼 보인다.

Formstack의 2023 보고서에 따르면 파일 업로드 시 진행률 표시가 없는 폼은
완료율이 12% 낮다.

→ `_uploadProgress` 변수를 UI에 연결하여 진행률 바 표시.

<br>

### 4. 임시저장 복원 다이얼로그를 닫을 수 없다 `S-004`

`mls_quick_registration_page.dart:142-168`에서 임시저장 확인 다이얼로그가
`barrierDismissible: false`로 설정되어 있다. Firebase 응답이 지연되면
사용자가 이 다이얼로그에 갇힌다. 타임아웃도 수동 닫기 옵션도 없다.

→ 10초 타임아웃 후 자동 닫기, 또는 닫기 버튼 추가.

<br>

### 5. 주소에서 지역을 잘못 추출할 수 있다 `S-005`

`mls_quick_registration_page.dart:236-252`에서 주소 문자열에 `"경기"`가 포함되어 있는지
확인하는 방식으로 지역을 판별한다. 이 문자열 매칭이 실패하면 기본값 `'SEOUL'`이 할당된다.

예를 들어 "인천광역시 경기대로 123"이라는 주소는 `"경기"`를 포함하므로
경기도로 잘못 분류된다. 결과적으로 매물이 엉뚱한 지역의 중개사에게 배포된다.

→ 주소 API 응답의 구조화된 시도 코드를 사용하여 지역 판별.

<br>

### 6. 등록 완료 후 다음에 무엇을 해야 하는지 안내가 없다 `S-006`

등록 성공 다이얼로그(`mls_quick_registration_page.dart:2814-2909`)에
체크마크 아이콘과 배포된 중개사 목록이 표시된다. 그러나 "중개사에게 알림이
발송되었습니다"나 "방문 요청이 오면 승인하세요" 같은 구체적 다음 단계 안내가 없다.

→ 완료 다이얼로그에 다음 행동 가이드 추가.

<br>

## 대시보드 문제

### 7. 내 매물에 구매자가 얼마나 관심을 보이는지 알 수 없다 `S-007`

`BuyerInquiry` 모델(`buyer_inquiry.dart`)이 존재하고 구매자 문의 데이터가
Firestore에 쌓이지만, 매도자 대시보드 카드(`mls_seller_dashboard_page.dart:492-618`)에는
관심자 수나 조회수 뱃지가 없다.

부동산 플랫폼에서 "내 매물에 N명이 관심 있다"는 정보는 두 가지 역할을 한다:
- **리텐션** — "등록한 보람이 있다"는 확인. 직방의 "관심 N명" 뱃지가 이 역할을 한다.
- **가격 판단** — 관심이 많으면 가격이 적정하거나 저평가라는 시그널.

이 데이터가 없으면 매도자는 매물을 등록한 뒤 "아무 일도 안 일어난다"고 느끼고
플랫폼을 떠난다.

→ 매물 카드에 조회수 + 관심자 수 뱃지.

<br>

### 8. 매물 로딩이 실패해도 사용자에게 아무 말이 없다 `S-008`

`mls_seller_dashboard_page.dart:81-85`의 매물 스트림 `onError` 콜백은
`Logger.error()`로 로그만 남기고 UI에 아무것도 표시하지 않는다.
네트워크 오류로 매물 로딩이 실패하면 대시보드가 빈 채로 남아서
사용자는 매물이 없는 건지 에러인 건지 구분할 수 없다.

같은 패턴이 `mls_property_service.dart:244-247`에도 있다. 쿼리 실패 시
빈 리스트를 반환하여 에러가 완전히 숨겨진다.

→ 에러 시 "매물을 불러올 수 없습니다. 다시 시도" 메시지 표시.

<br>

### 9. 거래가 완료된 매물을 숨기거나 정리할 수 없다 `S-009`

`sold` 상태의 매물이 "거래완료" 필터에 계속 남는다. 거래가 쌓일수록
대시보드가 지저분해지지만 아카이브나 숨기기 기능이 없다.

→ "완료 매물 숨기기" 토글 또는 자동 아카이브.

<br>

## 방문 요청·협상 문제

### 10. 중개사를 승인한 다음에 무엇을 해야 하는지 모른다 `S-010`

방문 요청을 승인하면 `mls_property_detail_page.dart:2051-2078`에서
"방문 요청이 승인되었습니다. {중개사명} 중개사와 연락처가 교환되었습니다."만 표시된다.

매도자 입장에서는 "중개사가 전화를 하는 건지? 내가 먼저 해야 하는 건지?
방문은 언제 잡히는 건지?"가 불명확하다.

→ 승인 완료 시 "중개사가 방문 일정을 조율할 예정입니다. 연락처: 010-XXXX-XXXX" 안내.

<br>

### 11. 방문 일정을 앱 안에서 조율할 수 없다 `S-011`

`visit_request_quick_sheet.dart`로 승인/거절은 가능하지만, 구체적 방문 일정 조율은
"전화하세요"로 끊긴다. 거래 흐름이 플랫폼 밖으로 빠지면 이후 데이터 추적이 불가능하다.

<br>

### 12. 중개사 메모가 2줄로 잘리고 전체를 볼 수 없다 `S-012`

`visit_request_quick_sheet.dart:310-320`에서 중개사의 메시지가 `maxLines: 2`로 잘린다.
전체 내용을 보는 확장 버튼이 없어서, 중요한 조건이나 요청사항을 매도자가 놓칠 수 있다.

→ 탭하여 전체 메시지 보기.

<br>

### 13. 카운터오퍼가 실제로 저장됐는지 확인하기 어렵다 `S-013`

`mls_property_detail_page.dart:932-982`에서 카운터오퍼 제출 시 성공 SnackBar가
뜨면서 동시에 시트가 닫히고 매물 데이터가 리로드된다.
사용자는 SnackBar를 볼 틈도 없이 화면이 바뀌어서 "실제로 보내진 건지" 불안하다.

→ 제출 후 시트를 닫기 전에 확인 상태를 잠시 보여주기.

<br>

## 핵심 욕구 충족 현황

| 매도자가 원하는 것 | 충족 여부 | 근거 |
|-------------------|:-----:|------|
| 빠른 등록 | 충족 | 3단계 완료 (`mls_quick_registration_page.dart:479-499` switch case 0,1,2) |
| 등록 중 피드백 | 미충족 | 가격/전화 검증 없음, 업로드 진행률 미표시 (S-001~003) |
| 내 매물 수요 확인 | 미충족 | 관심자 수·조회수 미표시 (S-007) |
| 중개사 선택권 | 충족 | 승인/거절 구현됨 |
| 적정 가격 판단 | 충족 | 시세 비교 구현됨 (`market_price_page.dart`) |
| 거래 진행 추적 | 부분 | 상태 변경은 가능하나 방문·협상 흐름 불완전 (S-010~013) |

## 개선 순서

| 순서 | 할 일 | 난이도 | 근거 |
|:----:|-------|:------:|------|
| 1 | 관심자 수 뱃지 (S-007) | 중 | 매도자 리텐션의 핵심 지표. 직방·네이버부동산 모두 제공하는 기능 |
| 2 | 전화번호 검증 (S-002) | 하 | 정규식 한 줄 추가. 잘못된 번호 → 중개사 연락 불가 → 거래 실패 |
| 3 | 업로드 진행률 (S-003) | 하 | 변수가 이미 선언되어 있어 UI 연결만 필요 |
| 4 | 스트림 에러 표시 (S-008) | 하 | `onError` 콜백에 SnackBar 한 줄 추가 |
| 5 | 승인 후 안내 (S-010) | 하 | 다이얼로그 텍스트 수정 |
| 6 | 지역 감지 로직 수정 (S-005) | 하 | 잘못된 지역 배포 → 매물 노출 실패 |
| 7 | 방문 메시지 전체 보기 (S-012) | 하 | 정보 누락 방지 |
| 8 | 방문 일정 인앱 조율 (S-011) | 중 | 거래 흐름을 플랫폼 안에 유지 |
